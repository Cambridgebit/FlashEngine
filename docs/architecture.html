01 / Architecture

六层单向调用架构

上层只依赖下一层：调度逻辑不碰硬件细节，硬件差异全部收在后端层。目标模型与投机方法各自经注册表解析，ModelRunner 只消费适配器与统一的提交契约。

为什么是单向的：后端可以换内核、换 KV 布局、换图实现，但调度层看到的是同一种「同质批 + block table + slot」；模型层可以加草稿，但执行层看到的是同一种「一轮返回 m+1 个已接受 token」的提交契约。
02 / Runtime

一次请求的生命周期

普通路径每步 schedule → run → postprocess；投机路径为 step_spec()：预填充阶段同时喂草稿模型，解码阶段每步跑一整轮投机。

STEP 01

接纳 / 分词

请求进入 waiting 队列，generate() 分词后按 token 预算决定是否可入批。

STEP 02

预填充 prefill

长 prompt 跨多个调度步分块处理，逐块写入分页 KV；投机时同步捕获 aux 隐层并让草稿模型吃同一 chunk。

STEP 03

解码循环

未完成请求组成 batch，每步一次前向各出一个 token；投机时一步 = 一整轮验证，可提交多个 token。

STEP 04

抢占 / 补块

逐 token can_append/may_append 补块，不足则 LIFO 抢占并释放 KV，回调 drop_spec_state。

STEP 05

回传

达到 max_tokens 或 EOS 后拼回文本；服务端每产出新 token 即唤醒 HTTP 线程推流。

公平轮转的连续批处理

有 waiting 且有 running 时，schedule() 按 _prefer_decode 在 prefill 与 decode 之间交替； 每步仍是同质批——因为后端 attention 内核不接受 prefill/decode 混合批。一侧无进展立即试另一侧，两侧都无进展才抛错，不再静默空转。

max_num_batched_tokensmax_num_partial_prefillspartial prefill 计入 max_num_seqs

服务端驱动模型

单个后台线程统一 step() 驱动所有排队请求，HTTP 线程只负责收发与推流；引擎初始化时跑一次 max_tokens=2 的 dummy 生成，把 decode/spec kernel 冷启动前移（实测首请求 0.604s → 0.067s）。

03 / Speculative Decoding

投机解码：一轮多个 token

三种草稿共用同一套「起草 → target 一次验证 → 接受最长匹配前缀 → 采样 bonus」的提交契约，被拒草稿不会进入前缀缓存。差别只在草稿如何产生提案。

EAGLE3 · 链式草稿

小草稿模型串行猜 k 个 token，每一步以前一步输出为种子；主模型一次前向批量验证。

# shifted draft 流口径
位置 p 的行:
  embed  = tok@p+1
  条件   = fc(aux@p)   # look-ahead
  预测   = tok@p+2
冷启动首轮走 eagercarry 按 seq_id 保存

DFlash · 块草稿

一次非因果前向并行产出 k 个提案，没有链式循环，草稿轮延迟更接近常数。

# 每轮三步
① 上下文追加  v_aux[0..m]
② 块草稿     k 个提案并行
③ verify     [anchor, 提案×k]
k = block_size − 1共享 target embed / lm_head

DSpark · Markov head

同样的并行块骨干，串接 vanilla 低秩 Markov head：逐位置在 base logits 上加前一个 token 的偏置。

base = block_forward()   # k 行并行
for pos in range(k):
  logits = base[:, pos]
         + markov_bias(prev)
  prev   = sample(logits)
固定 k（confidence head 已加载未启用）

一整轮投机在图内如何流动

为什么必须有图

投机轮把 kernel 数量放大数倍，host 侧 launch 开销会吃掉草稿收益。实测三硬件一致：eager spec 无收益甚至负收益——4070 上 spec 收益依赖图，CoreX 上 spec eager 仅 11.3 tok/s 而图路径 103.7 tok/s。

跨轮状态与冷启动

batch 组成每轮都会变，位置索引只在单次回放内自洽，所以状态一律按 seq_id 存字典：spec_carry（采样行隐层 + draft1）、spec_hidden（aux 行 m）、spec_cold（冷启动标记）。prefill 后首轮无 carry → 整批走 eager，之后进图。

05 / Memory

KV 分页与前缀缓存

KV 按固定 block 分页，block 级 xxhash 复用只覆盖 prefill 阶段；投机提交的 token 不参与哈希，避免被拒草稿污染缓存。

命中：直接复用已算好的 KV 未命中：本步继续计算并登记哈希 310P 块草稿：被块查询覆盖的末块永不登记

CUDA 默认 kvcache_block_size=256，因此短于 256 token 的共享前缀不命中属于预期；要观察命中，需要一个至少整块的固定 system / tools 前缀。 Agent 工作流数据集实测（4070 · k=3 · 24 请求）：命中 23，TTFT 中位 38.9ms vs 关缓存 121.2ms（−68%），吞吐 +12.6%，E 两侧不变。

target KV：block hash

逐块链式哈希，命中即复用物理块；--no-prefix-cache 会连哈希计算与查找一起关闭，便于做冷/热 TTFT A/B。

CUDA / CoreX 草稿：CPU 快照

块草稿的上下文 KV 由 aux 重投影而来，与分页 token KV 是两种内容，故走稠密缓冲，并把可缓存块的投影结果快照到有界主机内存（上限 1 GiB，LRU 淘汰）。cache_hit_validator 保证：target 块命中但快照已淘汰 → 整体视作未命中、正常 prefill。

Ascend 310P：分页 NZ 草稿 KV

每层独立 FRACTAL_NZ 草稿 KV，与 target 共用物理块索引与 slot，用非因果 SplitFuse 读取；靠「末块不登记哈希」避免污染，不需要主机快照。

代价与对照：快照路径在冷 prefill 多一次 D2H，收益要用 --num-repeats（同 prompt 连跑，第 2 次起全命中）对照；前缀缓存只降 TTFT，对稳态吞吐还略负哈希开销。
06 / Graph Capture

图捕获与优雅降级

普通解码按 batch 桶各录一张图；投机解码一整轮录一张图。任何捕获失败都打印告警、释放图池、回落到同构 eager 路径——不崩引擎。

图内必须全静态

  • 元数据在 host 预展开填 pinned，图内只做 copy_ / scatter；
  • 禁止捕获期 host 同步（.item() / tolist()）、动态形状、index 写与动态 Add；
  • 310P 的接受判定用 float 静态比较，绕开 AICPU Add；
  • padding 复位条件是 n < bucket，且切片轴序为 vs[n:, :]——轴序或条件任一写错，并发下真实序列的 verify 槽会被清成 −1，表现为输出全「！」。

图在 CoreX 上是刚需：eager decode 仅 7.8 tok/s，kernel launch 税被厂商 torch 放大；图后 bs=1 72.9 / bs=8 415.8（TPS sweep 9.3×，远超 4070 的 +23%）。板卡连续高负载会触发温度告警，bench 之间需留冷却间隔。

接受长度 E 是主信号

E = 1 + 每轮接受数。位等门对 aux 口径错误不敏感，E 才是最终判据：该配置应显著 > 2，若 E ≈ 1–1.2 先查 aux 换算与 embeds 是否过了 input_layernorm。

thinking 口径会改变 E

同 seed 同题集单变量对照（CoreX）：thinking-on E=1.748 / 85.3 → --no-think E=2.125 / 101.3。历史锚点全部是 thinking-off，对比时须两边一致。

低接受负载别开 spec

中文散文负载 E 仅 ~1.15–1.19，两个引擎都负收益（本引擎 61.7 → 59.7，vLLM 66.7 → 64.4，跨引擎互证）。高接受负载（coding / temp0）收益 +64% 以上。

对表警告：同命令同机冷态 vs 热态可差 ~1.6×（no-spec 42.6→69.8、spec 60.1→106.8，E 不变），来自持续负载下的热降频。TPS 落差先排除降频，再怀疑代码。
块草稿现状：DFlash / DSpark 在 main 上目前只有机械冒烟（合成 mini draft 跑通 config 派生 → warmup → eager 轮 → 图捕获 → 回放 → 读回，图/eager 与 base/spec 位等），尚无真实草稿权重的 TPS / E 锚点；310P 分页 DSpark 也待实机验收。
