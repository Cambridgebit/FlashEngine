# Qwen3.5 在 Ascend 310P 上的优化分析

本报告针对当前 Python 引擎，结合源码和开发板 `192.168.16.118` 的 `vllm018` 容器实测。Qwen3.5 当前支持文本 dense/MoE 的普通推理与 DFlash，限制为 TP=1、fp16/bf16；310P 实际使用 fp16。量化和 DSpark 组合目前被支持矩阵拒绝。模型的全注意力使用分页 KV，GDN 层另维护卷积和递归状态；DFlash 验证后须按接受位置恢复状态。

## 当前基线

板卡容器内的 Qwen3.5 模型实现、Ascend 后端和 benchmark 脚本与本地对应文件 SHA-256 一致；其他文件没有做完整一致性验证，因此结果对应板卡工作区，不宣称完整等同当前本地提交。使用 Qwen3.5-4B/9B，单序列、greedy、thinking 关闭、关闭前缀缓存、预热 1 条、3 条 coding 题、每条最多 64 token、最大上下文 2048、显存利用率 0.5。TPS 是排除首 token 的稳态解码吞吐，TTFT 是进程内首 token 延迟。

| 模型 | 模式 | 稳态 tok/s | TTFT 中位数 | TPOT 中位数 | 接受长度 E |
|---|---|---:|---:|---:|---:|
| 4B | 普通图 | 15.8 | 770 ms | 63.16 ms | — |
| 4B | DFlash k=7 | 32.9 | 804 ms | 31.90 ms | 4.283 |
| 9B | 普通图 | 9.4 | 803 ms | 106.05 ms | — |
| 9B | DFlash k=15 | 21.0 | 810 ms | 50.01 ms | 5.100 |

两组投机图分别回放 46/46 和 40/40 轮，均无 eager 回退。历史同口径 4B DFlash 32.8、9B DFlash 22.5 tok/s；本次 9B 数值较历史值低约 7%，只有一次测量，不能判定回归。原始日志在板卡 `/data2/q35opt/logs/`，本地记录见 [板卡基线](../scratch/q35opt/board/baseline.md)。

4B 另测相同构造方式的不同长度提示，每档三次、中位数：34、126、264、517 token 的 TTFT 分别为 758、789、855、1008 ms。说明短提示有显著固定成本，长度增长仍增加总延迟；这组测试本身不能把耗时全部归因于 GDN。

## 优先方向

1. **GDN 预填充**：310P 的参考路径在 [qwen3_5.py](../flashengine/models/qwen3_5.py) 的 `chunk_gated_delta_rule` 中对 64 行执行 63 次前向替换；4B 和 9B 均有 24 个 GDN 层。这是值得剖析的候选瓶颈，尤其对于短提示的固定开销。不能仅凭与不同架构 8B 的 TTFT 差值推算各算子的耗时。应先做真实输入的分段剖析，再评估融合算子或稳定的分块求解，并覆盖长上下文、分块 prefill、前缀恢复以及投机状态正确性。

   本次研究了用矩阵幂倍增替换前向替换：数学上等价，但会改变浮点运算顺序。板卡隔离副本的 4B eager 小样本中，短提示 TTFT 790→334 ms，548-token 提示 1020→606 ms；5 个短提示输出相同，第 6 个长提示输出明显异常。这是单次探索，**候选未通过正确性验证，不应合入或用于服务**。CPU NumPy 模拟中高相关 key 的合成输入也观察到数值失稳；它只是风险证据，不证明实际模型中具体的失稳原因。相关实验脚本在 [研究目录](../scratch/q35opt/analysis/fast_chunk.py)，并非生产实现。板卡算子微基准的首次尝试未完成，不能据此报告算子级加速比。

2. **DFlash 滑窗草稿**：`config.py` 对需要因果或窗口掩码的草稿关闭分页草稿路径，因为当前分页算子只支持全局非因果。历史记录中 4B 修正滑窗语义前后 k=7 为 36.8→32.8 tok/s，但语义和路径同时改变，这只是机会量级，不是可直接恢复的同语义收益。本次实际图回放率为 100%，因此不支持把差距归因于图回退。可评估支持窗口语义的融合注意力或分页算子；必须核对位置、窗口边界、草稿 KV、前缀缓存及图回放，再做同语义 A/B。

3. **投机长度调优**：历史同负载 4B 的 k=7 优于默认 k=15，本次 k=7 为 32.9 tok/s、E=4.283；9B 此次 k=15 为 21.0 tok/s、E=5.100。最优 k 依赖模型、提示词和负载，不能直接推广；对实际业务分别测吞吐、TTFT、接受率和图回退。项目当前将 CLI 的 k=3/4 视为未显式指定，扫描时应核对启动日志中的实际值。

4. **前缀缓存**：完整块边界保存 GDN 状态，命中时还要满足目标 KV 和草稿状态的有效性；短前缀和无共享前缀的请求没有收益。4B 的 SSM 状态约 48 MiB/边界，另有卷积状态，默认 256 MiB 快照预算大致可容纳五个边界。预算是缓存条目数，并不等于可命中的连续前缀长度：只需末个命中边界的 recurrent 快照，且还受 KV/草稿状态限制。应对真实多轮工作负载比较冷/热 TTFT、命中块数和快照淘汰，避免把历史 CUDA 结果当作 310P 实测。

5. **量化、批量及 DSpark**：Qwen3.5 的量化检查点和 DSpark 当前均被支持矩阵明确拒绝。接入 W8A8 需要覆盖 GDN 投影、加载映射、尺度与状态精度，并对长上下文和投机接受率验收；Qwen3 的量化收益不能直接套用。DSpark 需要匹配目标模型并带训练好的 Markov 头的草稿权重，单纯放开注册不能证明收益。增加并发可以摊薄权重读取，但 GDN 状态池随序列数和验证宽度增长；Qwen3.5 的实际聚合吞吐、内存占用和延迟需在板卡另测，不能用 Qwen3 的批量结果代替。

## 后续板卡实验：分块求解（2026-10-30）

在隔离副本中把 64 行求解拆成 4 个 16 行块，块内保留原前向替换、块间使用矩阵乘法组合；主引擎未应用此改动。4B、同基准口径下，普通路径 TTFT 中位数从 770 ms 降至 494 ms，稳态吞吐 15.8 tok/s；DFlash k=7 的 TTFT 从 804 ms 降至 546 ms，稳态吞吐 32.7 tok/s，E=4.283。各数字为小样本实验，跨运行会有环境波动。

六条提示、最多 32 token 的初步检查中，候选普通/投机与原版均逐 token 一致；扩展到 coding 数据集中实际取得的 10 条提示、最多 128 token 后，候选与原版普通路径仅 6/10 完全一致，投机路径 7/10 一致。原版自身普通与投机路径也仅 7/10 一致，候选自身为 8/10。测试结果不能确定分歧是否仅由浮点误差和接近并列的 logits 导致；**候选尚未通过严格正确性门，不应合入**。板卡日志位于 `/data2/q35opt/logs/compare_long.log`、`bfs_4b_base.log` 和 `bfs_4b_k7.log`。

另一种块内倍增的候选在六条短样本中，普通与投机路径仅 5/6 一致，而原版同样本为 6/6，因此也未通过。对真实 4B 权重的单次探针观察到长提示中严格下三角矩阵的最大绝对行和约 53.6；探针样本有限，短提示数据还包含引擎预热调用，只能作为数值压力线索。算子微基准两次尝试长时间未完成并已停止，不能报告循环耗时占比。

## 上游 310P 自定义算子探针（2026-10-30）

开发板 `vllm018` 的 `vllm_ascend` 为 `0.18.0rc2.dev28+g7b3aa263a`，torch-npu 为 `2.9.0.post2.dev20260401`。显式导入 `vllm_ascend.vllm_ascend_C` 后，`_C_ascend.npu_recurrent_gated_delta_rule_310` 和 `npu_causal_conv1d_310` 均注册。其安装包自带环境脚本指向构建时 `/tmp/vllm-ascend`；仅设置 Python 注册而未配置实际 `ASCEND_CUSTOM_OPP_PATH` 时，调用报缺少 infershape。隔离进程将该变量指向 site-packages 中真实 vendor 目录后可调用；未更改容器全局环境。

以 CPU 生成的 4B 头数/维度合成输入（key heads=16、value heads=32、head dim=128）进行一次测试：递推算子 1/2/8 行输出有限，相对 FP16 状态参考的最大输出绝对误差分别为 0、2.38e-7、1.53e-5，状态最大绝对误差分别为 6.10e-5、2.44e-4、2.44e-4；这些是单种随机数据、非端到端精度证明。FP32 状态被算子明确拒绝，而本项目使用 FP32 SSM 状态。因果卷积单步（8192 通道、宽4、单槽）写回的活动与非活动槽均与参考一致；输出最大绝对差 0.00390625，逐位相同约 73.6%。图模式、padding、连续批处理、真实权重及长跑正确性尚未验证。

一个简化的单行 NPUGraph 计时得到融合算子 0.149 ms/次；另一独立运行的融合算子为 0.300 ms/次，同轮简化 FP32 torch 递推为 0.219 ms/次。两轮不稳定，且两条路径精度、算子边界和布局不同，不能用作加速比或完整模型性能结论。探针脚本存于 `scratch/q35opt/lead/test_upstream_gdn.py`、`test_upstream_conv.py` 与 `bench_upstream_gdn.py`。未修改生产引擎，不能将上游 FP16 状态路径直接替代现有 FP32 状态路径。

## 上游递推算子的隔离引擎实验

仅在板卡 `/data2/FlashEngine_upstream` 副本接入 `npu_recurrent_gated_delta_rule_310`，启用 FP16 额外状态池，实验仅支持普通 decode、关闭投机与前缀缓存；不计入主仓改动。引擎 Qwen3.5-4B 六提示 eager 短样本与原版 5/6 完全相同，分歧发生在第 3 条，说明 FP16 状态和归一化变化不能当作严格等价。

普通图、单序列、三条 coding 提示、128 输出 token、无前缀、greedy/no-think，同机交替两组：原版分别 15.8/15.8 tok/s，上游候选分别 16.4/16.4 tok/s（约 +3.8%）；候选图回放 381/381、0 fallback。此前候选首测亦为 16.4 tok/s。数据量小，且方案保留额外 FP32 和 FP16 双状态池、未完整纳入显存规划；不代表生产可用。该原型在每次 prefill 后全池同步 FP32→FP16，chunked prefill、前缀恢复、抢占和并发语义未经验证。投机路径尚未接入。实验脚本为 `scratch/q35opt/lead/patch_upstream_gdn.py`，板卡日志 `/data2/q35opt/logs/paired_{base,upstream}_{1,2}.log`。

## DFlash 八行上游递推试验

在隔离副本中，将单序列 k=7 的目标 verify 递推改用上游 310P 算子：先把 carry 复制到独立验证行首槽，逐行写 8 个 FP16 状态，读回接受数后复制 `count-1` 行至主槽。单算子合成测试 8 行均有限、未碰 dummy，最大状态误差 2.44e-4；这不是跨请求或长序列正确性验收。

整模型 Qwen3.5-4B、原版 3 条 coding / 128 token / 无缓存 / 贪心口径，实验版 spec graph 捕获成功、88/88 回放、0 回退，稳态 32.4 tok/s、E=4.511；先前原版同口径为 34.4 tok/s、E=4.511。候选只测一次，约低 5.8%，不构成精确性能归因。原型另外保留两种状态池，每层发生 carry 拷贝、类型及布局操作，也改变归一化和状态精度；未覆盖并发、prefix、chunked prefill、接受数状态及质量验收。首次图捕获因 capture 内 CPU→NPU 常量复制失败，改为设备侧构造后图捕获通过。该方案未合入。

## 已合入：草稿注意力按实际上下文缩窄列宽（2026-10-30）

**诊断**：4B、DFlash k=7、同负载下只改 `--max-model-len`，E 保持 4.511 不变：

| max_model_len | 稳态解码 |
|---:|---:|
| 512 | 36.7 / 36.8 tok/s |
| 2048 | 34.4 / 34.4 tok/s |

草稿稠密注意力按 `max_model_len` 列计算（实际 ctx≈48），列宽是纯浪费：`forward_block(..., max_ctx)` 一直传 `config.max_model_len`。

**改动**（`flashengine/engine/model_runner.py`）：实现从「单一窄列宽」升级为**上下文分桶**（2026-11-23）：

- 桶阶梯默认 `(2048, max_model_len)`（`FLASHENGINE_DFLASH_CTX_LADDER=2048,8192` 可扩展），启动时为每个窄桶各捕一套整轮图，
  整宽图默认**不捕**（`FLASHENGINE_DFLASH_CTX_FULL=1` 恢复），整体开关 `FLASHENGINE_DFLASH_CTX_BUCKETS=0`。
- 回放时按「本批最长序列 + 本轮 k+1 行」选最小桶，桶宽同时作为①草稿稠密缓冲宽度、②`_ctx_bound()` 传给分页注意力算子的上下文上界；
  超出最大窄桶的批次直接走 eager 轮（计入 `ctx_fallbacks`）——实测 eager 比整宽整轮图快 2-3 倍。
- 被裁掉的列都在掩码外（-inf），softmax 权重为 0，故数值不变；KV 布局、前缀机制和算子都不动。
- 窄桶必须使用独立 graph pool：不同列宽的整轮图共用同一 pool 会按首图布局复用显存，实机复现 `507011` 地址越界，这是实现上的关键约束。

**分桶实测**（2026-11-23，`/data/Qwen3.5-9B-lora642-fp16` + `Qwen3.5-9B-DFlash` k=7，业务数据 1170-token prompt、24 token、贪心、`--max-num-batched-tokens 2048`、util 0.70；同一份代码只改 `--max-model-len`）：

| max_model_len | 桶宽 | 每轮回放 | TPOT p50 | 稳态解码 |
|---:|---:|---:|---:|---:|
| 2048 | 2048（整宽） | 176 ms | 55.3 ms | 18.1 tok/s |
| 4096 | 2048 | 195 ms | 61.1 ms | 16.4 tok/s |
| 8192 | 2048 | 225 ms | 71.1 ms | 14.1 tok/s |
| 32768 | 2048 | 385 ms | 127.5 ms | 7.9 tok/s |

同一 32K 配置在改造前（整宽整轮图 + 稠密宽度 32768）为每轮 515 ms / TPOT 183 ms，分桶后分别为 385 ms / 127 ms。
**稠密路径的残余**：即使读取固定 2048 列，图内高级索引写入仍以按 `max_model_len` 分配的全尺寸张量为目标。隔离 NPUGraph 探针固定 8 个更新行和 6 层，eager 与回放写入均通过检查。`max_num_seqs=8` 时，单个 K 或 V 张量的写入耗时从 2K 的 7.93 ms 增至 32K 的 105.89 ms，固定宽度 gather 从 0.87 增至 3.48 ms。K/V 两份写入合计增加约 196 ms，与整轮实测增加的 209 ms 同量级。`max_num_seqs=1` 时，单份写入增量约 23.1 ms。探针验证了尺寸敏感点，未测量 CANN 内核的具体访存量。

### 310P 滑窗分页草稿

板上 Qwen3.5-9B 草稿的前五层是 4096-token 滑窗，第六层是全局注意力。具备 legacy SplitFuse 的运行时现在可使用分页 K/V 写入。窗口层只读取覆盖有效窗口的页，首个部分页和每行因果边界由掩码裁剪。全局层读取全部有效历史。图回放前原地更新各桶的长度、块表和掩码，维持捕获地址稳定。缺少对应后端能力时仍走稠密路径。

在 Atlas 310P 使用融合 9B 权重、k=7、单并发、两条英文 coding 提示各生成 32 token，2K 和 32K 配置的 TPOT p50 分别为 45.26 和 45.27 ms，两组均为 22.1 decode tok/s、E=3.765，各回放 17 轮且无 eager 回退。8K 配置下，分页图与稠密参考对 12、4111、4511 token 的混合批次及 4511-token 重复请求生成了相同的 token 序列。该重复请求的分页配置启用了前缀缓存，稠密对照关闭了前缀缓存。

固定四条英文 coding 请求，各生成 64 token，2K/32K 均回放 57 轮、无回退，生成 token 全部一致。四序列图的 `replay` 段（含元数据推送）中位数分别是 226.6/223.3 ms。

HTTP 测试使用 8 条请求、输出上限 128 token，2K 与 32K 使用相同输入和输出 token 总数，两档均无请求错误。下表每格按 2K / 32K 顺序列出。

| 英文 Spec-Bench coding | 4 | 41.745 / 30.300 | 44.55 / 56.65 |

## 为什么 Qwen3.5 的 DFlash 加速比低于 Qwen3（架构 vs 310P）

结论：**主因是 GDN 混合架构本身，310P 实现差距是第二层放大；接受长度 E 不是原因**
（Qwen3.5 的 E 4.28–5.10，不低于 Qwen3-8B 的 4.878）。加速比 ≈ `E × 单步 ÷ 一轮`，
E 相近时全部差别落在“一轮等于几个普通步”：

| 模型 / 硬件 | E | 单步 | 一轮 | 一轮/单步 | 加速比 |
|---|---:|---:|---:|---:|---:|
| Qwen3-8B，310P（k15） | 4.878 | 91.7 ms | 129.7 ms | **1.41** | 3.45× |
| Qwen3.5-9B，310P（k10，本负载最优） | 5.000 | 105.6 ms | 200.8 ms | **1.90** | 2.62× |
| Qwen3.5-9B，310P（k15） | 5.100 | 105.6 ms | 220.8 ms | **2.09** | 2.43× |
| Qwen3.5-4B，310P（k7，本负载最优） | 4.283 | 63.0 ms | 123.8 ms | **1.96** | 2.18× |
| Qwen3.5-2B，CUDA 4070（融合 GDN 后，k15） | 4.083 | 17.6 ms | 30.3 ms | **1.73** | 2.36× |

读法：

- 纯注意力的 Qwen3-8B，16 行验证只比单步多 41%：权重只流一遍，多出的行几乎免费。
- **Qwen3.5 在 CUDA、且已启用融合 GDN 递推时，一轮仍是单步的 1.73 倍** → 架构层面就有差距，
  不是 310P 独有。
- 310P 上进一步到 1.9–2.1 倍 → 310P 实现再叠加约 0.2–0.35 的轮成本。

**架构原因（Qwen3.5 的 24 个 GDN 层）**

1. 验证行必须**逐行推进递归状态**：第 2 行依赖第 1 行推进后的状态，不能像注意力那样把多行
   并进一次权重流。8 行验证 = 8 次状态递推。
2. 状态流量大：每行每层读+写 2 MB FP32 状态（4B：`[32,128,128]`）。8 行 × 24 层 × 2 MB × 2
   ≈ **768 MB/轮**，按 310P 实测约 176 GB/s 折算 ≈ **4.4 ms**，纯注意力模型没有这笔开销。
3. 还要支持回滚提交（接受 m 个后把 `count-1` 行状态写回主槽），实现上需要额外的状态记录与拷贝。

**310P 实现差距（把架构差距放大）**

| 现状 | 后果 |
|---|---|
| GDN 行递推走纯 torch 小算子链，无 CUDA 的融合行核 | 4B 实测 **97.9 µs/行/层**，8 行 × 24 层 ≈ **18.8 ms/轮**（约占一轮 15%） |
| 上游 310P 融合递推只接受 **FP16 状态**（本项目 FP32）；其 MTP 窗口上限为 8，更大窗口需另行适配 | 用融合核需改状态精度；大 k 受算子限制 |
| 旧版滑窗草稿走稠密掩码路径 | 历史对照中缩窄列宽使 4B 提升 5.5%。当前支持 legacy SplitFuse 的 310P 可按页执行滑窗草稿 |

**量化上限**：以 4B 为例，若融合行核把 18.8 ms 压到 ~4 ms，一轮 123.8 → ~109 ms，
一轮/单步 ≈ 1.73，加速比约 **2.5×**；再给滑窗草稿接因果分页注意力，有望 **2.6–2.7×**。
但要追上 Qwen3-8B 的 3.45×，需要让“多行验证几乎免费”，而 GDN 的逐行状态递推与状态流量
不会消失；除非改用把整个验证窗口做成一次三角求解的算法（TreeWY 一类），属于算法级改造。

**公开证据（第三方资料，未在本板复现）**

- TreeWY 把 GDN 混合模型的投机验证当作独立问题，用验证窗口上的严格下三角求解替代逐行推进：
  <https://browse-export.arxiv.org/pdf/2608.20961>。
- 一份 GDN 混合模型投机设计记录给出经验式 `speedup ≈ (1+j̄)/(c_v + K·r + (1+j̄)/S)`，
  自由文本下约 **1.6–1.9×**：
  <https://raw.githubusercontent.com/john-rocky/coreai-model-zoo/refs/heads/main/knowledge/spec-decode-hybrid-verify-design.md>。
- 递归状态按投机块占页会显著吃内存（记录为约 150 MB/槽、48 层），因此默认窗口常取 3 而非 8：
  <https://raw.githubusercontent.com/SciSharp/TensorSharp2/refs/heads/main/docs/speculative_decoding.md>。
- vLLM 为 GDN 投机维护 “RecoverSSM” 回放记录并讨论其内存占用：
  <https://app.semanticdiff.com/gh/vllm-project/vllm/pull/62625/overview>；
  混合模型递归状态内存瓶颈的 RFC：<https://github.com/vllm-project/vllm/issues/54080>。
- vLLM-Ascend 把 `MAX_MTP` 提到 16 时明确 **310P（v310）不在范围内、保持 8**：
  <https://github.com/vllm-project/vllm-ascend/pull/11236>。
- 310P 的 GDN 预填充仍是 chunked torch + 自定义 chunk 前向算子：
  <https://raw.githubusercontent.com/vllm-project/vllm-ascend/main/vllm_ascend/_310p/ops/fla/chunk_gated_delta_rule.py>。

**因此**：不能把差距归因于“310P 慢”——同一块 310P 上纯注意力的 Qwen3-8B 仍有 3.45×；
也不能只归因于架构——CUDA 上融合 GDN 后 Qwen3.5 的轮/步比已从 2.4 降到 1.73。
正确表述是：**GDN 架构决定了上限，310P 缺少融合行核与窗口注意力进一步压低实际值**。
后续最值得做的是把已验证可用的 310P 融合递推用到 verify 多行上，并给滑窗草稿接因果分页注意力。

## 草稿前向的带宽底账（2026-11-23，310P 实测）

想再压「一轮里草稿那 34 ms」，先量清它花在哪。三层证据：

**① 310P 上 ND 与 FRACTAL_NZ 权重差 3.5 倍**（`.tmp/probe_gemm_310p.py`，M 为解码行数）：

| 形状 | `F.linear`(ND) | `matmul(x, w.T)` | `F.linear`(NZ) | `npu_linear`(NZ) |
|---|---:|---:|---:|---:|
| gate_up M=8 K=4096 N=24576 | 4.343 ms / 46 GB/s | 4.324 / 47 | **1.211 / 166** | 1.195 / 169 |
| qkv M=8 K=4096 N=4608 | 0.776 / 49 | 0.775 / 49 | **0.251 / 151** | 0.245 / 154 |
| lm_head M=7 K=4096 N=151936 | 24.738 / 50 | 24.772 / 50 | **7.065 / 176** | 7.013 / 178 |

→ 引擎把 Linear/LM-head 权重转 NZ 是必需的（启动摘要 `Linear/LM-head weights=FRACTAL_NZ`
已生效）；`npu_linear` 与 `F.linear(NZ)` 等价，`decode_linear_backend=selective` 无额外收益。

**② 草稿一次前向的内部拆解**（`probe_draft_parts.py`，eager、k=7、rows=8、ctx≈1227、19 轮）：

| 段 | 每轮 | 说明 |
|---|---:|---|
| `forward_block` 合计 | 56.2 ms | eager 且每段同步，图内实测约 34 ms |
| 6 层合计 | 43.0 ms | 7.16 ms/层 |
| ├ 注意力（含 qkv/o/norm/RoPE） | 23.0 ms | 3.84 ms/层 |
| │ ├ `store_kvcache` | 2.05 ms | 0.34 ms/层 |
| │ └ `dflash_paged_attention` | 4.06 ms | 0.68 ms/层 |
| └ 其余 linear（qkv/o/gate_up/down） | 20.9 ms | 3.5 ms/层，NZ 理论 2.3 ms/层 |
| lm_head（k=7 行 × 151936） | 11.8 ms | NZ 理论 7.1 ms |

**③ 一轮的总带宽账**：目标 18 GB（32 层，其中 24 层 GDN）+ 目标 lm_head（8 行 × 151936，约 1.24 GB）
+ 草稿 6 层 3.4 GB + 草稿提案头 1.24 GB ≈ **23.9 GB**；按实测 NZ 峰值 166–176 GB/s → **理论 144 ms/轮**，
实测 159 ms ⇒ **已用到带宽上限的 90%**。剩余约 15 ms 是 8 行 verify 的逐行 GDN 小算子（≈3 ms/行）、
掩码/元数据（≈5 ms）与接受回读。

**结论**：草稿那 34 ms 里 ~27 ms 是权重流量（3.4 GB 层权重 + 1.24 GB 提案头），不是能用融合算子消掉的
调度开销；把 15 ms 松弛全收掉也只有 +10%。真正能成倍改变绝对吞吐的是**减少权重字节**：

- 草稿提案头换**缩减词表**（`draft_vocab_size` + `d2t/t2d`，本仓已支持该格式）→ 提案头 1.24 GB 降到
  约 0.26 GB（32k 词表），一轮 −6 ms（≈+4%）；需要这样的草稿检查点。
- 目标 + 草稿走 **W8A8 int8**（310P 有真 int8 通路）→ 23.9 GB → ~12 GB，一轮 ~80 ms，绝对吞吐接近
  翻倍；`docs/SUPPORT_MATRIX.md` 里 Qwen3.5 目前只有 fp16/bf16，int8 是新增工程。

**试过的候选（已否决）**：怀疑 `_forward_rows` 的逐行 `self.ssm_cache[slot] = state`（2 MB 高级索引写，
`_forward_decode` 里实测 605 µs）是每行 3 ms 的来源，改成「攒满一段后一次切片写 + 固定 fp32 缓冲」
（多一次 fp32→fp16 整段 cast，约 20 MB/层流量）。结果业务 c1 一轮中位 **159.0 → 164.7 ms**（408 轮），
输出 token 逐位一致 ⟹ 逐行写不是主因，多出的 cast 反而更贵，已回退（`git stash` 存档）。
