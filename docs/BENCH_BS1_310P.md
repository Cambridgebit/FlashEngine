# 单并发（BS=1）六配置压测 · Atlas 300I Duo (310P)

> **状态**（2026-11-24）：310P 单卡单并发、`--max-model-len 40960 --max-num-seqs 8 --gpu-mem-util 0.70 --block-size 16` 下六种配置 × 中英 × 五类负载的实测台账。数字是**每个场景 1 次请求**的客户端读数（多轮为 4 轮中位数），不是稳态吞吐；首条请求含图捕获与权重首读，另行标注。

## 方法

- 部署：板卡 `192.168.16.118` 容器 `vllm018`，`/data2/fe-structured`（提交 `2c205c2`），venv `/data2/fe-t5-venv/bin/python3`。
- 服务：`python -m scripts.openai_server <MODEL> [--spec-model <DRAFT>] --backend ascend310p --max-model-len 40960 --max-num-seqs 8 --gpu-mem-util 0.70 --block-size 16 --no-think`，`FLASHENGINE_VLLM_GEMM=1`。
- 客户端：`scratch/q35opt/stress6.py`（板上 `/data/hostmem/stress6.py`），流式 + `stream_options.include_usage`；TTFT = 首个正文/工具增量，解码 tok/s = 输出 token / (E2E − TTFT)。
- 去缓存污染：每个场景首条消息带随机 nonce `[cfg-lang-xxxxxxxx] `；但第 2 场景的小文档与大文档**共享前缀**，8B（纯全注意力）会命中前缀缓存，9B（GDN 快照预算不足）不会——见「注意事项」。
- 每配置 16 个请求（中英各 8），共 96 个请求；原始读数 `/data/hostmem/stress6.jsonl`，服务端日志 `/data/lora/stress_<cfg>.log`。

## 结论

1. **DFlash 对 Qwen3.5-9B 的收益集中在解码**：同负载解码 9.2 → 14.1–16.6 tok/s（+53%~80%），长上下文 TTFT 基本不动（7.8 s → 7.9 s，prefill 由 GDN 主导，草稿只占 ~5%）。
2. **8B 的解码更快但 TTFT 有缓存优势**：8B 全注意力没有 GDN 快照，前缀命中真实生效，第 2 场景 TTFT 0.16–0.21 s（9B 是 1.6–1.8 s）；不要把这 10 倍差当成纯 prefill 能力差。
3. **LoRA 的代价在两端**：普通 LoRA 比基座慢约 10%（解码 9.2 → 8.3 tok/s），TTFT 也涨 15–25%（4K 场景 7.8 s → 10.0 s，含首请求权重栈首读）；LoRA + DFlash 能拿回大部分（12.9–15.2 tok/s），仍比纯 DFlash 低约 8%。
4. **工具调用两跳都正常**：六配置全部 `finish=tool_calls` → 第二跳 `stop`，无协议泄漏；工具首跳 TTFT 比同尺寸普通请求高 1.5–2×（受 tools schema 与约束路径影响）。
5. **多轮对话**：9B 每轮 TTFT 0.86–1.3 s（上下文 150–300 token），8B 0.15 s 级；轮间增量约 50–80 token，符合 ChatML + 无 think 的口径。

## 注意事项（读表前必看）

- **单位不同不可横比**：`tool_call` 行的解码 tok/s 标「跳-」，因为首 token 与结束几乎同时（输出 25–46 token 全在第一帧里），除零保护后无意义。
- **首请求含图捕获**：`q35_lora_dflash` zh 长上下文 TTFT 10.7 s、`q35_8b_dflash` zh 长上下文解码 5.7 tok/s 都是**该配置第一条请求**（spec 图按上下文宽度桶懒捕获）。看第 2 条以后（en 同场景 6.5 s / 9.8 tok/s）才是稳态。
- **8B 的第 2 场景是缓存命中读数**：TTFT 164–210 ms 对应 ~900 token 输入，物理上必然来自前缀复用（小文档是大文档前缀）；9B 因为 GDN 快照 49 MiB/份、默认预算 256 MiB 只装 5 份，复访被判未命中，才需要 1.6–1.8 s。要测 8B 的真冷 prefill，需要换 nonce 前缀，本表未做。
- **不是吞吐压测**：BS=1、每个场景 1 次（多轮 4 次），用于端侧 Agent 的**单请求延迟画像**；并发/持续负载请用 `scripts/bench_concurrent.py`。
- **看 E 之前先看输出长度**：`E` 的上限是 `k+1`（k=7 → 8.0，k=15 → 16.0），并且**末轮截断会按满接受计**。本表里 `tool_answer` 英文 15 token 的 `E=8.00`（LoRA+DFlash）/`E=5.67`（DFlash）、`out=6` 那几行全部是这个效应，只能当上界，不是「草稿 100% 命中」。
- **英文 E 系统性高于中文是可复现的**，不是测量错误：同一份英文材料（1,176 token）重测三次 E=3.31/3.31/3.25、中文（3,697 token）2.44/2.44/2.32，TTFT 3.5 s vs 9.0–12.4 s（长度差 3.1×，单位 prefill 成本一致）。归因是英文散文的逐 token 分支更少 + 更贴合草稿权重的训练分布；同机早前 Spec-Bench coding 负载英文 E≈5.7 也是同一方向。跨语言比 E 时要固定「同一段内容」的口径。
- L 值差异：中文长文档 3,697 token、英文 3,332 token（同一 5,200/15,000 字符目标），两语言不完全等长。
